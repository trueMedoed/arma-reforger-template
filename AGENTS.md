# Старт нового мода Arma Reforger

Эта памятка предназначена для разработчика и агентов, создающих проекты в каталоге Mods. Учитывайте явные указания пользователя и более конкретные инструкции внутри существующих проектов. Не применяйте шаблон задним числом к уже настроенным модам без необходимости.

## 1. Постановка задачи

- Уточните назначение мода по запросу пользователя: игровой мод, помощник Workbench или диагностический инструмент.
- Создайте отдельную папку с понятным названием, например `Conflict Spawn Helpers`.
- В корне создайте `TODO.md`: цель, исходные наблюдения, план реализации, проверки и критерии готовности. Отделяйте подтверждённые факты от предположений.
- Создайте `README.md`: назначение, текущий статус, путь к addon.gproj, порядок открытия и известные ограничения.
- Если создан только каркас, прямо укажите, что функциональность ещё не реализована.
- Сразу при создании папки мода создайте docs/workshop с DESCRIPTION.md, RU_DESCRIPTION.md и CHANGELOG.md по правилам ниже; не откладывайте эти файлы до публикации.

## 2. Структура addon-проекта

Ориентир для структуры — соседний `Vehicle Spawn/ME_Vehicle_Spawn`. Для минимального каркаса можно также посмотреть `Conflict Spawn Helpers/ME_Conflict_Spawn_Helpers`.

Пример:

```text
New Mod/
  .gitignore
  README.md
  TODO.md
  docs/
    workshop/
      DESCRIPTION.md
      RU_DESCRIPTION.md
      CHANGELOG.md
  ME_New_Mod/
    addon.gproj
```

Создавайте `Scripts/Game`, `Scripts/WorkbenchGame`, `Prefabs`, `Configs`, `worlds` и другие каталоги по мере необходимости. Не копируйте скрипты, миры, GUID, базу ресурсов и личные настройки другого мода целиком. Отдельный диагностический addon нужен только при реальной необходимости.

Минимальный `addon.gproj` по образцу локальных проектов:

```text
GameProject {
 ID "ME_New_Mod"
 GUID "<NEW_16_HEX_GUID>"
 TITLE "ME_New_Mod"
 Dependencies {
  "58D0FB3206B6F859"
 }
 Configurations {
  GameProjectConfig PC {}
 }
}
```

Перед сохранением замените ID, TITLE и placeholder GUID. `ME_` — принятый здесь префикс, если пользователь не выбрал другой. GUID проекта должен быть новым, состоять из 16 шестнадцатеричных символов и не совпадать с GUID других локальных addon-проектов. Значение `58D0FB3206B6F859` — зависимость от базовой игры, используемая в существующих проектах; её не заменяют GUID нового мода. Дополнительные зависимости добавляйте только при необходимости.

`resourceDatabase.rdb` и метаданные ресурсов создаёт Workbench. Не генерируйте их вручную и не переносите из другого проекта. В существующих локальных проектах resourceDatabase.rdb хранится в Git; для нового проекта можно следовать этому образцу после первичного открытия в Workbench.

## Названия плагинов Workbench

Для плагинов Workbench ставьте префикс `[ME] ` только у корневой категории в меню Plugins, например `category: "[ME] Conflict Spawn Helpers/Diagnostics"`. Дочерние категории (`Diagnostics`) и названия команд (`name: "Check spawn points"`) оставляйте без префикса. Даже для единственной команды задавайте корневую категорию, а не добавляйте `[ME]` к её названию. Префикс `ME_` в именах классов, файлов, ресурсов и логов от этого правила не меняется. Используйте одинаковые видимые названия в интерфейсе, README и документации Workshop.

## 3. Проверка в Workbench

- Откройте новый `addon.gproj` в Arma Reforger Tools / Workbench и дождитесь сканирования ресурсов.
- Проверьте отсутствие ошибок загрузки проекта и зависимостей.
- После добавления скриптов отдельно проверьте компиляцию соответствующих модулей.
- После реализации создайте подходящий тестовый мир или используйте согласованный сценарий; сравните результат с критериями из TODO.
- Не приравнивайте успешное открытие пустого проекта к проверке работоспособности будущего мода.
- Обновляйте README и TODO по фактическим результатам. Если проверку выполнил пользователь, так и укажите.

Для помощника редактора отдельно проверьте, что визуальные подсказки не меняют игровой спавн, не сохраняют лишние сущности в миссию и корректно очищаются при переходах Edit/Game и смене мира.

## 4. Git и первый коммит

- До `git init` проверьте, нет ли существующего репозитория в папке проекта или родительском каталоге. Не создавайте вложенный репозиторий случайно.
- Для самостоятельного нового мода используйте отдельный репозиторий в его корневой папке. Выполняйте инициализацию и коммит в рамках запроса пользователя; если запрошен полный старт проекта с Git, дополнительных подтверждений для этих шагов не требуется.
- В `.gitignore` исключите личные настройки инструментов, логи и временные файлы. Не исключайте исходные ресурсы и необходимые метаданные без причины.
- Перед первым коммитом просмотрите список файлов: не добавляйте пароли, токены, личные настройки, временные выгрузки и скопированные файлы базовой игры.
- Добавьте каркас, README, TODO и необходимые ресурсы. Пример сообщения: `Initialize <mod name> addon project`.
- После коммита проверьте `git status` и сообщите пользователю хеш коммита и состояние рабочей папки.
- Создание локального репозитория не подразумевает создание репозитория на GitHub, настройку remote, push или публикацию в Workshop.

## Тексты для Workshop с первого дня

- `docs/workshop/DESCRIPTION.md` — английский текст для полей `Summary` и `Description`. Отделяйте служебные пояснения от текста для копирования. Описывайте назначение, реализованные возможности, использование и известные ограничения.
- В `Summary` простыми словами объясняйте пользу мода: что пользователь сможет сделать и какую проблему решит. Предпочитайте одно-два коротких предложения с конкретным результатом вместо перечня технических возможностей, внутренних названий классов и жаргона. Например: «Размещайте базы и источники припасов Conflict без догадок: заранее смотрите, где появятся объекты и куда будет обращена табличка доступа к складу припасов». Используйте этот принцип, а не копируйте пример для любого мода. Не обещайте «без проблем», «идеально» или гарантированный результат, если это не подтверждено; подробности и ограничения раскрывайте в `Description`. Сохраняйте одинаковый смысл пользы в английском Summary и русском переводе.
- `docs/workshop/RU_DESCRIPTION.md` — русский перевод для внутренней сверки с теми же разделами. По умолчанию для публикации предназначен английский текст. Обновляйте обе версии вместе при изменении возможностей мода.
- `docs/workshop/CHANGELOG.md` — заметки к выпускам с английским блоком для Workshop и русским переводом для сверки. Начните с `Unreleased`; внесите фактический номер и дату публикации после подтверждения выпуска. Дату подготовки не выдавайте за дату публикации.
- На этапе каркаса явно помечайте тексты как черновики, а задуманные возможности — как планируемые. Не представляйте нереализованные функции и невыполненные проверки как готовые.
- Для текста полей используйте обычный текст, буквальные маркеры `•` и нумерацию, чтобы он был пригоден для копирования без Markdown-разметки.
- Добавьте в README ссылки на все три файла. Ссылку на репозиторий или страницу Workshop добавляйте только при наличии известного адреса; не придумывайте URL.
- Ориентир: `Vehicle Spawn/docs/workshop` и `Conflict Spawn Helpers/docs/workshop`. Переносите структуру, адаптируя содержание к новому моду; не копируйте чужие возможности, историю выпусков и результаты проверок.

## Минимальный результат старта

Отдельная папка проекта, addon.gproj с собственным GUID, README, TODO, .gitignore и три начальных файла в docs/workshop: DESCRIPTION.md, RU_DESCRIPTION.md, CHANGELOG.md. Открытие в Workbench и Git-коммит отмечены как выполненные только после проверки. В итоговом сообщении укажите, что уже создано и что ещё предстоит реализовать.
